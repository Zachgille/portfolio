TriageFlow

A support desk for many companies at once: tickets, customer replies, internal notes, assignments, SLA checks and audit logs. Every company’s data sits in the same PostgreSQL tables, and none of it is visible to the others.

Stack
TypeScript, Next.js, NestJS on Fastify, PostgreSQL, Prisma, Redis, BullMQ, Clerk
Testing
Integration tests against live PostgreSQL, k6 load tests
Source
github.com/Zachgille/triageflow

The pieces

A Next.js front end, a NestJS API that owns every business rule and authorization check, PostgreSQL for tenant data, and a separate worker for scheduled jobs. Clerk only handles sign-in.

One database, many tenants

TriageFlow uses pooled tenancy: every tenant’s rows live in shared tables and carry a tenant_id. It’s the cheapest way to run many tenants and the easiest to get wrong, because one query that forgets its tenant filter leaks another company’s tickets. That tradeoff is the project’s first decision record, along with the options I passed on, a database or a schema per tenant.

So isolation can’t depend on remembering a WHERE clause:

  • Every repository method takes a RequestContext holding the request ID, user, tenant, membership and resolved permissions. Controllers never call Prisma directly.
  • Relations between tenant-owned rows use composite foreign keys that include tenant_id, so the database itself rejects a ticket whose requester or assignee belongs to another tenant.
  • Clerk handles sign-in and nothing else. Roles and permissions live in TriageFlow’s own tables, and every protected endpoint checks them. The interface hides controls you can’t use, but the API is what enforces it.

Tests that try to break it

The integration suite runs against a real PostgreSQL database with a test auth provider, and most of it attempts things that should fail. Some of the test names:

  • prevents a Tenant A user from listing Tenant B tickets
  • does not read or comment on another tenant ticket through Tenant A context
  • does not let Tenant A privileges grant Tenant B mutations
  • rejects cross-tenant requester and assignee references
  • allows viewers to read tickets but not mutate them
  • does not create ticket or audit rows when SLA policy lookup fails

From api.live.integration-spec.ts, which also covers cursor pagination, internal-note filtering and transactional audit logs.

Finding the slow query

I seeded one large tenant with 50,000 tickets and 250,000 comments and pointed k6 at the API: 20 virtual users for five minutes. The default ticket queue, unfiltered and newest first, was the slowest list endpoint, with a p95 of 42 ms, about twice the filtered queues.

EXPLAIN ANALYZE showed why. The queues filtered by status, priority or assignee already had tenant-scoped indexes. The default queue didn’t, so PostgreSQL read the whole tickets table, threw away the other tenant’s rows and sorted what was left.

The fix was one index whose columns match the query: tenant first, then the same ordering that cursor pagination uses.

The index takes some disk and makes every ticket insert slightly more expensive. A support desk reads its queue far more often than it creates tickets, and created_at and id never change after insert, so I kept it.

All of this ran on my desktop (Intel i5-9600K, about 16 GB of RAM, PostgreSQL and Redis in Docker, the API in development mode). The absolute numbers say little about production; the before-and-after comparison is the point. The full write-up is in docs/benchmarks.

Background work

SLA breach checks and analytics rollups run in a separate worker process on Redis and BullMQ. Jobs get retried, so they have to be safe to run twice: unique constraints in the database mean a retried breach check can’t record the same breach twice. Workers go through the same tenant-scoped repositories as the API.

Decisions, written down

  1. 0001
    Pooled tenancyShared tables with a tenant on every row, rather than a database or schema per tenant.
  2. 0002
    Modular monolithOne codebase and one database plus a worker process, instead of services that would need distributed transactions.
  3. 0003
    Redis workersBullMQ for scheduled and retried jobs, which must be idempotent.
  4. 0004
    Tenant-scoped repositoriesEvery repository method takes a RequestContext; controllers never touch Prisma.
  5. 0005
    PostgreSQL indexingIndexes follow documented access patterns and are justified with query plans.
  6. 0006
    Clerk for auth, RBAC in the appIdentity comes from Clerk; roles and permissions stay in TriageFlow’s database.
