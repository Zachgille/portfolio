TriageFlow

A multi-tenant support desk designed around a simple obligation: every request must stay inside the right workspace, with the right permissions.

SYSTEM DESIGN

One application.
Explicit boundaries.

A modular monolith keeps business rules together; a separate worker process handles asynchronous work. Select a component to inspect its responsibilities.

01 / Web

Identity starts the request.

Clerk provides authentication. The Next.js client presents ticket queues, conversations, workspace flows, and permission-aware analytics. Hiding a control is a usability choice; the backend still checks every protected operation.

02 / API

Authorization stays with the backend.

The modular monolith resolves membership and permissions into a tenant-scoped RequestContext. Controllers delegate to services and repositories, which carry that context into tenant-owned data access.

03 / Database

Tenant boundaries reach the schema.

Tenant-owned tables and composite tenant relations support isolation. Ticket mutations and their audit records share transactional boundaries. Cursor pagination orders queues by created_at and id.

04 / Workers

Background work follows the same rules.

A separate worker process handles SLA breach checks and analytics rollups. Workers reuse tenant-scoped access rules; database uniqueness supports idempotency when jobs are retried.

THE ENGINEERING PROBLEM

A workspace is a
security boundary.

TriageFlow models tickets, customer replies, internal notes, assignments, audit logs, SLA checks, and analytics for multiple workspaces. Authentication identifies a user; application-owned memberships and roles determine what that user may do within a tenant.

I designed tenant isolation to be authoritative on the backend. Services and repositories receive RequestContext, and composite database relations reinforce tenant ownership. Internal notes are only returned to users with the corresponding permission.

VALIDATION

Test the denial path.

Live PostgreSQL integration tests exercise cross-tenant denial and permission boundaries. The repository also covers pagination, audit behavior, and transactional behavior using a dedicated test database and a test authentication provider.

  • Identity: Clerk authentication
  • Authorization: tenant-scoped roles and permissions
  • Data access: context-aware services and repositories
  • Evidence: database-backed integration tests

PERFORMANCE / MEASURE → INSPECT → CHANGE

A query plan made
the next step clear.

The unfiltered ticket queue used a sequential scan and top-N sort. A composite index aligned tenant selection with the queue’s ordering and changed the plan to an index scan.

The change

The index uses tenant_id, created_at DESC, id DESC, matching tenant-scoped queue reads and their cursor ordering. This ties the optimization to a measured access pattern.

What the result establishes

The improvement was measured on a local Windows machine with an Intel i5-9600K, about 16 GB RAM, PostgreSQL and Redis in Docker, and the API in development mode. It is a controlled benchmark, not a claim about production capacity.

TAKEAWAY

Correctness first.
Then make it faster.

The most useful part of this project is the connection between security rules, data modeling, and performance evidence. An interface can make permissions visible; the system still has to enforce them consistently at the point of access.
